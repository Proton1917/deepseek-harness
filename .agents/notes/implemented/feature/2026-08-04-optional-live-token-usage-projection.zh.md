# Agent Note: 可选的实时 token 用量投影

Status: implemented

[English](2026-08-04-optional-live-token-usage-projection.md) | 中文

## 问题

持久的 `tokenUsage` 会话投影会在提供方报告用量时变化，因此响应进行流式输出期间，composer 状态行保持不动。呈现插件可以估算阶段性输入量、输出量和吞吐率，但需要一个类型化的会话作用域通道，并且不能削弱持久的提供方用量契约。

## 决策

token-meter 的客户端词汇中包含 `liveTokenUsage`：这是一项由扩展插件提供的可选会话投影。它的输入与输出桶采用和 `tokenUsage` 相同的结构；`estimated` 用于区分启发式估算桶与经提供方校正的值，生产方能够测得时间区间时，`tokensPerSecond` 携带输出吞吐率。

内置 composer 状态行在 `liveTokenUsage` 存在时优先使用它显示输入与输出，将两者之和显示为不缩写且带分组分隔符的完整整数，估算值以 `~` 为前缀，未注册实时生产方时则回退到持久的 `tokenUsage` 投影。该总和等于计费输入（`uncachedInputTokens + cacheReadTokens + cacheWriteTokens`）加输出。缓存命中率始终来自 `tokenUsage`，因为缓存账目归提供方所有，无法可靠地进行流式估算。内置状态行不渲染吞吐率；插件可以通过 `conversation.composer.dock` 添加相应呈现，而无须修改 conversation 包。

实时投影不会成为计费、上下文压力或持久化的权威数据源。它的生产方负责估算、提供方校正、重试替换、中止回滚和更新频率。持久的 `tokenUsage` 投影仍是完整会话中精确提供方用量的数据源。

## 曾考虑的替代方案

**在内置 token-meter 插件中注册实时估算器。** 不予采纳，因为估算策略和更新频率属于呈现选择。如果由默认运行时负责二者，一项可选显示功能就会成为产品范围内的行为，还会写死部署需要控制的可调项。

**直接在 React 状态组件中推导流式总量。** 不予采纳，因为组件需要自行解释请求、分片、重试和中止事件。这会在渲染路径中重复会话投影逻辑，也会阻止其他客户端扩展使用同一状态。

**由外部插件替换整个内置状态行。** 不予采纳，因为插件只为增加一个变化字段，就要重复实现轮次、步骤、上下文压力、缓存用量和格式化逻辑。类型化投影让现有负责方继续保留这些字段，而单独的 dock 扩展可以负责吞吐率等附加行。

**通过 `tokenUsage` 发布估算值。** 不予采纳，因为消费方依赖该投影获取提供方报告的持久用量。混入估算值会使缓存账目和精确总量的含义变得模糊。

## 验证

composer 组件测试通过投影订阅驱动 `liveTokenUsage`，并验证输入、输出及二者不缩写的完整总和在流式输出期间持续变化、估算值带有 `~`，以及最终显示恢复为精确的提供方用量。token-meter 投影测试继续分别锁定持久用量与上下文压力契约。

## 后果

没有实时生产方时，默认组合保留现有的精确最终总量，且不显示吞吐率。插件无须替换内置状态条，即可提供持续变化的总量和额外一行 dock 内容。消费方与生产方新增一项客户端投影契约，其可选性与估算标记必须保持兼容。
